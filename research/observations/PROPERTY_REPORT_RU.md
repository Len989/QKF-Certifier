# Независимая цель после автоматического вывода наблюдений

14 сентября 2026. Первый законченный сценарий из плана v0.3: программа,
отдельная спецификация, проверяемый результат или конкретный контрпример.

## Результат

Новая проверка отличает правильное описание поведения программы от
выполнения требования к этому поведению. Все четыре исследуемых исходника
имеют корректные сертификаты своих моделей; только исходное условие
удовлетворяет требованию максимального допустимого результата.

| Условие | Максимальность при соблюдении границы | Только соблюдение границы |
|---|---|---|
| `trial <= bound` | Доказано: 49 совместных состояний, 980 переходов | Доказано: 49 состояний |
| `trial <= bound + 1` | Опровергнуто: выход выше границы | Опровергнуто |
| `trial < bound` | Опровергнуто: пропущен больший допустимый результат | Доказано: 51 состояние |
| `trial <= initialValue` | Опровергнуто: пропущен больший допустимый результат | Доказано: 28 состояний |

Положительные результаты относятся к ограниченной математической словной
модели для любой положительной длины полезного слова. Связь с Java по-прежнему
использует доверенный ограниченный фронтенд и правила разбиения слова;
переполнение JVM и произвольные знаковые входы не покрываются. Новых теорем
Lean в этом прогоне нет.

## Отдельно задаваемый контракт

Обозначим начальное значение через A, границу через B, необязательную маску
через O. Вызов использует положительную ширину w полезного слова и
дополнительный нулевой знаковый бит. Все четыре входных слова имеют w битов,
а O получается из `may & ~must` на этой ширине. Предпосылки: `A & O = 0`
и `A <= B`.

Разрешённые результаты образуют множество

`L(A,O) = { A | S : S — подмаска O }`.

Требование `bound`: выход Y принадлежит L(A,O) и удовлетворяет `Y <= B`.
Требование `maximum` дополнительно утверждает:

`для каждого Z из L(A,O), если Z <= B, то Z <= Y`.

A — наименьшее разрешённое слово. Поэтому `A <= B` обеспечивает непустоту
допустимого множества. Если `A > B`, вход находится вне предпосылок этой
проверки; сертификат не устанавливает, как API должен представлять пустоту.

Это контракт расширения начального значения необязательными битами.
Он не утверждает, что произвольный `initialValue` уже содержит все биты
входного `mustBeSet`. Такие условия вызывающей процедуры и полный совместный
носитель Graal относятся к отдельной задаче.

Спецификация передаётся проверяющему независимо от программы и сертификата.
Поддержаны два фиксированных контракта с версией схемы. Произвольные
предусловия и язык логических спецификаций пока не поддержаны. Изменённый
контракт получает отказ, а не незаметно ослабленную интерпретацию.

## Совместное наблюдение

Используется уже проверенный фактор поведения исходника. К нему добавляются
четыре вопроса порядка: A относительно B, Y относительно B, Z относительно B,
Z относительно Y. Z — независимо выбранный допустимый конкурент выхода,
а не второй запуск исходной программы.

Чтение идёт от младших битов к старшим. Если очередные старшие биты двух
слов равны, отношение порядка младших частей сохраняется. Если они различны,
отношение определяет старший бит: разность двух k-битных младших частей
строго лежит между `-2^k` и `2^k`. Это даёт точный трёхзначный переход
наблюдения порядка и индукцию по любой длине слова.

Алфавит состоит из всех 20 допустимых колонок
`(bound, must, may, seed, output, alternative)`.
Он независимо перечисляет входы спецификации, даже если исходная программа
часть из них не читает. Например, сравнение с `initialValue` не читает B,
но для проверки максимальности B всё равно пробегает все значения.
Проекция этих колонок в алфавит исходного фактора проверяется отдельно.

Производитель строит замыкание совместного наблюдения. Положительный
сертификат содержит исходное состояние и состояния с обоснованиями
достижимости. Проверяющий проверяет начало, каждый переход происхождения,
замкнутость под всеми колонками и отсутствие нарушения защищаемой цели
в каждом состоянии, принимаемом фактором источника.

Это конечный индуктивный сертификат: начальное наблюдение охвачено;
один шаг сохраняет принадлежность проверенному множеству; поэтому охвачены
слова любой длины. Квантификация по Z получается из полного независимого
выбора его допустимых битов. При непустом входном носителе нет принятого
выхода выше B или меньшего, чем некоторый допустимый Z не выше B.

Сертификат источника связывает принимаемые слова с его операционной моделью:
условия записи определяются общими срезами, вопросами сравнения и действиями
нижнего суффикса. Доверенный контракт одного нисходящего прохода даёт
завершение и единственный результат; запись сохраняет фиксированные биты.
Проверенные обратные строки и фактор сохраняют этот граф поведения.
Так замкнутое совместное наблюдение применяется к результату математического
исходного прохода. Сам Python-фронтенд и это соответствие всей JVM здесь
не формализованы.

В терминах QKF добавлены защищаемые вопросы отдельного потребителя к уже
полученному фактору. Его переходы остаются обоснованными вынужденными
строками; новое замыкание проверяет обязательства цели. Проверка конечного
совместного замыкания — стандартный приём. Самостоятельная новизна общего
алгоритма проверки инварианта здесь не заявляется.

## Контрпримеры

При `bound + 1`: ширина 1, A=0, O=1, B=0. Программа возвращает Y=1,
что превосходит B. Выбранные сырые аргументы: must=0, may=1.

При строгом `< bound`: ширина 1, A=0, O=1, B=1. Программа возвращает
Y=0, хотя допустимо Z=1. Граница соблюдена, максимальность нарушена.
Сравнение с `initialValue` даёт аналогичный контрпример.

Проверяющий каждого отрицательного пакета повторяет путь по проверенному
фактору, восстанавливает целые входы, непосредственно исполняет
математический исходный проход и отдельно вычисляет нарушение цели.
Для этого не нужны Java, SMT и поиск производителя.

Изменение хеша цели само по себе недостаточно: тест берёт положительный
сертификат безопасной границы для строгого сравнения, заменяет привязку на
цель максимальности, и проверка отвергает пакет на защищаемом обязательстве.
Сертификат модели также не принимается за сертификат свойства.

## Проверки реализации

Прошли 59 тестовых методов: 47 прежних и 12 новых. Новые проверки включают
13 изменений положительного пакета, 7 изменений контрпримера, подмены
предусловий и цели, повторное связывание слабой цели, подмену исходника,
исчерпание бюджета, сохранность выходных файлов и свежие процессы с `-O`.
В свежих процессах заблокированы производители, старые адаптеры, модули
нативного испытания, `subprocess` и SMT-библиотеки.

Для четырёх исходников напрямую выполнен Java-метод на всех 2 954 наборах
сырых параметров ширины 1–3, удовлетворяющих условию непересечения масок.
Всего 11 816 вызовов. На каждый исходник 1 859 входов также удовлетворяют
`A <= B`, а 1 095 находятся вне этого предусловия и учтены отдельно.

Независимый конечный оракул перечисляет разрешённые числовые результаты.
Проверены 4 368 отношений с альтернативами на исходник, всего 17 472.
Расхождений наблюдений с целочисленной целью и Java с математическим
исполнением нет. В пределах допустимой области обнаружены:

| Исходник | Выходов выше границы | Допустимых, но немаксимальных выходов |
|---|---:|---:|
| Исходный | 0 | 0 |
| Смещение +1 | 185 | 0 |
| Строгое сравнение | 0 | 185 |
| Сравнение с начальным значением | 0 | 491 |

Эти конечные испытания проверяют реализацию; универсальный математический
вывод обоснован замыканием, полнотой колонок и словной индукцией. Схема
целевых сравнений дополнительно проверена на 270 случайных наборах слов
ширины от 1 до 256 битов. Случайные проверки не подменяют индукцию.

## Использование

Из корня репозитория, каталог вывода должен быть новым:

```sh
python -m research.observations.run_property_experiment reproduction/property --native
python -O -m research.observations.property_cli check reproduction/property/original.java --source-certificate reproduction/property/original.source_certificate.json --spec reproduction/property/maximum.spec.json --certificate reproduction/property/original.maximum.certificate.json
```

Для повторного вывода использовать `derive` вместо `check` и новый путь
`--certificate`. Требование `--spec` обязательно для обеих команд.
`property_cli spec maximum.spec.json` создаёт шаблон максимальности;
`--claim bound` выбирает только соблюдение границы.

Коды выхода: 0 — свойство доказано; 1 — проверен контрпример; 2 — исчерпан
бюджет; 3 — вход или сертификат отвергнут. Проверка отрицательного пакета
возвращает 1 даже при корректности самого пакета: он опровергает свойство.
Повреждённый пакет возвращает 3. Существующие файлы не перезаписываются.

Основные файлы: `upper_spec.py`, `property_kernel.py`, `property_producer.py`,
`property_cli.py`, `word_execution.py`. `property_validation.py` и
`run_property_experiment.py` нужны для независимых испытаний. Все четыре
источника, два контракта и восемь доказательных результатов сохранены в
`evidence/property/`. Эксперимент добавлен в GitHub Actions.

Это исследовательский вход, ещё не новая возможность устанавливаемого
публичного пакета. Покрытие KnownBits не изменено. Следующий шаг плана —
вывод наблюдений для другой структуры операций через общие правила.
