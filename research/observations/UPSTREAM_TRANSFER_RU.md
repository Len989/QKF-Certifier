# Следующий независимый этап: исходный примитив OpenJDK

База разработки — опубликованный `main` на
`49372a463bd4a5a86b7962deaa4f38ddecd8234f`. Работа не использует общий язык
формул прогона 2, композицию прогона 3 или целевую формализацию прогона 4.
Уже принятый PR №8 не удаляется и не меняется. Отложенная интеграция не
подменяется этим небольшим изменением.

## Обнаруженное ограничение

Старый `extract_mask` узнавал только локальную сокращённую реализацию:

```java
static long mask(int width) { return width == 64 ? -1L : (1L << width) - 1; }
```

В реальном OpenJDK 25 `CodeUtil.mask` использует явную проверку диапазона,
`if/else` и шестнадцатеричную константу. Одна лишь замена сокращённого
метода этой реализацией приводила оба профиля к `unsupported`, ещё до
получения математической модели. Это ограничение связывания исходников,
не обнаруженная ошибка Graal или OpenJDK.

## Точная граница расширения

Распознаётся ещё ОДНА фиксированная форма метода, с сохранением всех
условий, операторов, типов литералов и возвращаемых значений OpenJDK.
Переименование параметра, пробелы и комментарии допустимы, как раньше.
Это не новый общий разбор шестнадцатеричной арифметики, не произвольный
интерпретатор Java и не пропуск неизвестного примитива.

Её числовое обоснование на физических входах `0 <= bits <= 64`:

* Для 0–63 выражение `(1L << bits) - 1`, вычисленное по модулю `2^64`,
  устанавливает ровно `bits` младших битов. При 63 промежуточный сдвиг
  имеет отрицательную знаковую интерпретацию, но вычитание даёт корректную
  маску `Long.MAX_VALUE`.
* Для 64 константа `0xffffffffffffffffL` обозначает ту же 64-битную маску,
  что `-1L`. При нулевой ширине получается 0.
* Проверка `assert` истинна на указанном диапазоне. Её наличие не даёт
  разрешения предполагать новые условия вызывающего метода.

Нативный тест исполняет все 65 допустимых ширин и шесть недопустимых
значений с включёнными assertions. Исследовательская параметрическая
семантика по-прежнему использует математическую маску; это НЕ доказательство
исполнения JVM с произвольной шириной и НЕ новая теорема Lean.

Хеш старой формы примитива не изменяется. Новая форма получает собственную
привязку. Пакеты для одного исходника не принимаются для другого, даже при
совпадении численного действия. Идентификаторы существующих схем сохранены;
старый проверяющий не обязан распознавать новую форму исходника.

## Настоящие внешние входы

`upstream_transfer.py` фиксирует две полные ревизии `IntegerStamp.java` из
`oracle/graal` и полный `CodeUtil.java` из `openjdk/jdk` (JDK 25 GA). Для каждого
указаны неизменяемый commit и Git blob ID. Перед анализом проверяются точные
байты; затем сохраняются также SHA-256 и размеры. Комментарии и лицензии
исходных файлов не удаляются.

Вход анализатора — явная конкатенация двух неизменённых файлов с разделителем.
Это **лексический пакет источников**, а не одна компилируемая единица Java.
Он позволяет старому ограниченному фронтенду выбрать реальный метод и
связанный примитив. Проверка нативного исполнения компилирует только точные
выбранные регионы с уже существующей тестовой обвязкой. Сборка Graal целиком,
разрешение всех Java-импортов и доказательство достигающего пути не заявлены.

Для каждого источника независимо проверяются четыре прежние фиксированные
цели: `maximum`, `bound`, `cyclic_successor`, `membership`. Сам файл Graal без
поставленного примитива остаётся неподдержанным: никакая скрытая заглушка не
подставляется. Неудачи поддержки или бюджета сохраняются как таковые, не как
контрпримеры программы.

Это **подготовительная проверка переноса источника**, а не завершённый
замороженный внешний прогон 5: две ревизии одного семейства кода нельзя
выдавать за восемь независимых алгоритмов. Изменение распознавания примитива
разработано по просмотренному исходнику. Для будущего замороженного набора
движок нужно фиксировать уже после этого изменения.

## Запуск

Сохранить три исходных файла с фиксированных адресов, перечисленных в
`UPSTREAM`, как `graal_reference.java`, `graal_revision.java`, `jdk25.java`.
Из корня репозитория, используя новый каталог вывода:

```sh
python -m research.observations.upstream_transfer run inputs reproduction/upstream --native
python -O -m research.observations.upstream_transfer replay reproduction/upstream
```

Без `--native` выполняются математические и числовые проверки, но нативный
статус будет `not_run`. Повторная проверка не вызывает производителя и заново
строит источник и независимую цель из исходных файлов и фиксированных правил.
Отсутствующий пакет даёт `no_certificate`, а не подтверждение старого отчёта.
Код завершения команды эксперимента означает завершение эксперимента, не
правильность всех программ: отдельные вердикты находятся в `SUMMARY.json`.

Workflow `Upstream primitive transfer` загружает закреплённые исходники,
проверяет их идентичность, запускает Python 3.10/3.12 и Java 17, выполняет
старые и новые тесты, повторную проверку с запрещёнными импортами отложенных
модулей и сохраняет исходники, пакеты и результаты артефактами CI.

## Локальный контроль до публикации

14 новых методов прошли на локальной базе: четыре положительных фиксированных
цели, 18 прежних вердиктов после смены примитива, десять повреждений реализации,
границы исходных привязок, отсутствие неявного примитива, отдельные процессы
обычного Python/`-O` и нативная проверка маски. Это созданные регрессионные
случаи, не результаты полного внешнего эксперимента. Полные upstream-файлы
будут проверяться фактическим CI; его исходы публикуются отдельно по коммиту.
