# PR39: исполняемый контракт и учёт работы контрольного маршрута

Это первый этап roadmap v0.3, **не новый алгоритм вывода наблюдений**.
Модуль запускает сохранённый signed-путь принятого PR38 (unified.v6 / guarded
coverage), а по явно указанной стратегии — прежний конкретный precheck PR34
перед ним. Операции source/reduction/coverage/observations/targets не изменены.

## Что фиксируется

`qkf-semantic-request-v1` содержит исходный текст, точный source selection,
семантический `profile`, явный список `conditions`, независимый Boolean-потребитель,
силу гарантии, бюджет, стратегию и бюджет предварительного поиска. Неподдержанная
сила гарантии или неизвестная форма потребителя отвергается, а не ослабляется.

Профиль пока только `modular-lsb-signed-word-predicates-v1`: один входной int/long,
прежние равенства, маски, Boolean-потребители и уже поддержанные signed-атомы.
Сдвиги, произвольные циклы и новая Java-грамматика не добавлены. `conditions`
синтаксически проверяются в прежнем языке целей, **но непустой список пока даёт
`unsupported_conditions` без доказательства**. Нельзя получить успех, молча
отбросив предпосылку или подменив её желаемым результатом.

Гарантии `consumer_sufficient`, `exact_source_interface`,
`minimal_source_interface` различаются в запросе. Пока положительный covered-путь
оплачивает прежнее полное построение, даже если нужна только достаточность.
`achieved.source_interface` сообщает точность/минимальность только данной конечной
source-модели и потребителя её выхода, не глобально наилучшего интерфейса программы.
Конкретное опровержение может закрыть отрицательный вопрос без source-интерфейса;
оно НЕ объявляется получением запрошенного полного интерфейса.

## Использование

```python
from research.semantic_work.contract import make_request
from research.semantic_work.run import run, check

request = make_request(source, independent_target,
    guarantee='consumer_sufficient', strategy='covered', max_work=2_000_000)
report = run(request)
if report['proof'] is not None:
    verified = check(request, report['proof'])
```

```sh
python -m research.semantic_work.cli run request.json --output measured.json
python -m research.semantic_work.cli check request.json --proof proof.json --output checked.json
python -m research.semantic_work.experiment NEW_DIRECTORY
python -m research.semantic_work.replay EXISTING_DIRECTORY
python -O -m research.semantic_work.replay EXISTING_DIRECTORY
```

`run` возвращает report с `result`, отдельным `proof`, его полным размером и `work`.
CLI создаёт только новые файлы. Для внешнего check из отчёта передаётся именно
`report['proof']`, не весь измерительный отчёт. Публичный устанавливаемый `qkf`
не переключён. Это не очередной универсальный решатель и не production SDK.

## Доказательство и измерение — разные объекты

`qkf-semantic-control-proof-v1` связывает точный запрос с неизменённым старым proof.
Самостоятельный check заново проверяет source/target и старое доказательство,
пересчитывает новый результат. Он не импортирует метр, эксперимент или producers.
Неизменённый v6-checker по-прежнему принимает внутренние covered-сертификаты;
старый witness-checker принимает внутреннее конкретное доказательство.

Создание оболочки после уже проверившего результат старого producer не запускает
искусственный дополнительный replay. В эксперименте полные внутренние proof и
старые результаты сравниваются с прямым вызовом сохранённого control-пути.

`qkf-semantic-work-v1` — **диагностическая запись, не сертификат факта выполнения**.
Хеши и суммы счётчиков позволяют обнаружить порчу или несогласованную запись,
но не доказывают, что недоверенный процесс действительно выполнил столько работы.
Приёмка экономии требует воспроизводимого запуска закреплённого кода и guards.
Изменение telemetry не может заставить semantic checker принять неверное свойство.
Незавершённые исходы replay не объявляет доказательствами отсутствия решения.

## Единицы учёта

Общий `max_work` — число Python `call`-событий внутри `research.*`, исключая сам
`semantic_work`. Включены возобновления генераторов и все прежние helpers,
парсеры, поиск и встроенные перепроверки. Это **не CPU-инструкции, lambda/delta,
сложность доказательства или число нативных операций**. Разные версии Python могут
давать разные call counts. Превышающий лимит вход учитывается как последняя
попытка, но тело функции не исполняется. Старые локальные caps сохранены.

Один Meter может обслужить несколько `execute` в активной сессии. Счётчики не
обнуляются между повторениями, cache-запросами и fallback. `max_attempts` общий.
Процессный StopWork не перехватывается прежними `except Exception`, поэтому
исчерпание общего бюджета не превращается в прежний успешный результат.
После прерывания сохраняются уже раскрытые состояния и попытки переходов.

Дополнительные показатели (отсутствующий счётчик означает ноль):

| Поле | Точное значение |
|---|---|
| `source_parse_attempts/completions` | Все реальные вызовы и успешные возвраты старого frontend, включая replay. |
| `ir_word_nodes_produced_total`, `ir_atoms_produced_total` | Сумма размеров каждого заново полученного исходного IR; повторные разборы не скрыты. |
| `unique_ir_word_nodes/atoms` | Размеры различных полных исходных IR; это не глобальная конгруэнция термов. |
| `discovered_states` | Длина созданных списков covered-состояний во всех попытках, в том числе незавершённых. |
| `discovery_branch_attempts`, `completed_discovery_branches` | Начатые и завершённые producer-ветви отдельно. |
| `coverage_edge_rechecks`, `atomic_row_rechecks` | Повторная проверка этих объектов отдельно от открытия. |
| `observation_questions_created`, `pullbacks_attempted` | Работа прежнего наблюдательного producer, не новый ground-вывод II. |
| `separators_materialized` | Реально созданные прежние попарные свидетели, ещё не устранённые из discovery. |
| `target_states_created` | Сумма состояний произведений во всех попытках. |
| `whole_word_evaluation_calls`, `unique_whole_word_points` | Конечные IR-вычисления и уникальные точные входы, не число доказанных всех-ширинных фактов. |
| `fact_requests`, `unique_fact_requests`, `direct_fact_attempts`, `fact_cache_hits` | Отдельный журнал запросов будущих адаптеров; в текущем control этот механизм не вызывается. |

Проверяется и запрос нативного факта с настоящим повторным использованием
проверенного объекта: два запроса, одна прямая проверка и одно cache-попадание.
Сам `cache_hit` не наделяет запись истинностью — истину устанавливает evidence-checker.

`ground_input_terms` и `added_ground_terms` равны **null**, а не нулю: generic E
и его query-DAG появятся в PR40. Объём исходного signed IR уже учитывается, но
его нельзя назвать числом узлов будущего E. Новые forcing/lemma механизмы явно
помечены как не реализованные/не вызванные. Старые atomic-row проверки остаются
видимыми; они не выдаются за новый эффект D>S из PR38.

Wall-time охватывает входную проверку, доступные в процессе импорты, весь поиск,
встроенные проверки и упаковку результата. CLI-чтение/запись отдельно. Peak memory
через tracemalloc — Python-выделения после входа в измерение, включая инструмент;
это не RSS, не память Java и не полный peak процесса с уже загруженными модулями.

Профилировщик не подменяет функции, поэтому импортированный alias старого полного
построителя тоже обнаруживается. Это guard для закреплённого однопоточного Python
маршрута, не sandbox против reflection, отключения профилирования или нативных
расширений. Вложенные profiler/tracemalloc-сессии не разрешаются.

## Четыре не взаимозаменяемых вида информации

`NativeFact`: checker повторно получает значение источника на одном точном слове.
Это начальный конкретный тип, **не параметрическая лемма**; универсальные source
факты появятся в PR41. Значение, ширина и исходник проверяются, target не доказывается.

`AbstractSeparator`: checker PR38 проверяет заданное конечное представление и
разделяющую модель для пары на выбранном горизонте. Это не выполнение программы
и не доказательство универсального неравенства.

`ConcreteWitness`: неизменённый PR34 checker подтверждает настоящее расхождение
источника и отдельно заданной цели на конечной ширине. Только этот тип может
пройти отдельный шлюз `refutation`. Малоширинный результат не выдаётся за Java bug.

`Unresolved`: проверяется структура диагностического исхода, не истинность
теоремы об отсутствии решения. Ни этот тип, ни native-point факт, ни separator
не может стать положительным доказательством или source-refutation по receipt.
Объекты отделены от caller-словарей; pickle и обычное создание из receipt запрещены.

## Протокол и границы эксперимента

Регистрация `6e745eb43c11a27080b823eaf0e328b57b7045e6` хранит PROTOCOL,
фиксированные определения 18 случаев и hashes запросов **до записанного полного
эксперимента**. Предыдущие unit/smoke прогоны — открытая разработка. Это не holdout.

Все 18 случаев: direct v6, измеренный covered и измеренный concrete→covered.
Предварительный поиск явно выбирается, не становится новой стратегией по умолчанию.
Его успех, неуспех и исчерпание окна сохраняются; отсутствие свидетеля не успех.

Отдельно 5 чередующихся пар cold-process direct/wrapped, без profiling/tracemalloc.
У этих timing-only процессов действуют прежние backend caps и таймаут родителя,
но **не общий call-limit**: без профилирования этот ресурс не измеряется.
Их исходы и внутренние proof сверяются с основным проверенным запуском. Нельзя
выдавать такой timing-only запуск за применение той же resource policy.
Все попытки, stdout/stderr и таймауты сохраняются; автоматических retries нет.
Нельзя складывать instrumented и cold times или выбирать лучшую удачную попытку.

Будущие ablation-слоты и серии из 1/4/16 целей зарегистрированы для PR44/46,
но **не объявляются выполненными в PR39**. Ускорение, эффект I/II, новая Lean-теорема,
расширение языка или новый внешний Java-корпус здесь не заявляются.

Текущий workflow расширяется; исторические замки, статьи и результаты неизменны.
Дополнительный preserve-audit защищает все 1995 других принятых файлов PR38.
Следующий этап — PR40: самостоятельное запросное ядро II с собственным proof-DAG
и нижними моделями, используя существующий прототип и каталановские эталоны.
