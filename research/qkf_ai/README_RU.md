# QKF → AI: исполнимые интерфейсы и проверяемые действия

Это линия проекта из чата, перенесённая в GitHub начиная с Run26. Нумерация опытов из чата независима от PR и исследовательских профилей QKF-Certifier. Дальний ориентир — автоматически получать достаточный исполнимый интерфейс к новому окружению, переносить его на новые программы и подтверждать пользу относительно сильного обычного решения с учётом **всех** затрат.

Run26 завершён: [отчёт и дальнейший фокус](run26/REPORT_RU.md). Локально 29/30 PASS, GitHub Actions 30/30 PASS; поздняя смешанная пара воспроизведена, причина не установлена, выпуск CSV SDK остаётся заблокирован.

Текущий этап: [Run26 — диагностика границы SQLite commit/capture](run26/PROTOCOL_RU.md). [История и ограничения](run26/HISTORY_RU.md) объясняют, почему физическая согласованность эффекта и квитанции пока блокирует выпуск CSV SDK. Перенесены также сохранённые [отчёт Run25](history/run25/REPORT_RU.md), [аналитическая записка](history/run25/ANALYTICAL_MEMO_RU.md) и [разбор сбоя](history/run25/SOURCE_FAILURE_REVIEW_RU.md); внутренние пути этих неизменённых документов относятся к исходному архиву. Экспериментальный qkf_import из чата не является установленным CLI qkf-certifier.

Ближайшая последовательность:

| Этап | Проверяемый вопрос | Условие продвижения |
|---|---|---|
| Run26 | На какой границе возникает расхождение DB/journal/receipt? | Локализация причины и отдельное подтверждение исправления; успех нового стенда сам по себе недостаточен |
| Run27 (предложение) | Полезен ли достаточный интерфейс в новом многошаговом домене, если знания уже даны oracle? | Изменение планов, перенос на новые программы, практический выигрыш у strong ordinary/safe; затраты получения oracle-знаний отдельно |
| Run28 (предложение) | Может ли LLM получать эти знания эффективнее обычного learner? | Скрытые новые структуры, одинаковые условия, полные расходы обучения и исполнения |

Модули будущего продукта: адаптер наблюдений и действий; представление состояний/предикатов/эффектов со scope и evidence; генератор разделяющих вопросов и контрпримеров; проверяющий слой; планировщик; исполняющий SDK с recovery/idempotency; журнал и независимый evaluator; интерфейс человека. В Run26 проверяется только инженерная часть исполнения и доказательств о сохранённых файлах. Остальные модули не объявляются построенными или доказанными этим опытом.

CSV learner остановлен после Run23: локальное ускорение не компенсировало цену вопросов. Не требуется сохранять AI-механизм, если обычное решение лучше. Наша обычная реализация — тоже часть продукта. Дальнюю архитектуру проверяем отдельными falsifiable опытами, а не успехом unit tests.
