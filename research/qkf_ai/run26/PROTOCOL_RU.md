# Run26: граница commit, файлов и холодного восстановления

Дата регистрации: 5 октября 2026. Это диагностический опыт, а не выпуск SDK и не модельный AI-эксперимент.

## Исходная проблема

В Run25 сохранены четыре пары SQLite DB + journal, при штатном восстановлении которых остаются PRE-данные и POST-квитанция. Основная серия: 78/81 PASS; дополнение: 26/27 PASS. Причина не установлена. Оригиналы, их журналы, протоколы и отрицательные результаты не изменяются. В GitHub переносится небольшой воспроизводимый диагностический стенд и frozen исходники, а не сотни мегабайт исторических баз. Исторические результаты описаны отдельно в HISTORY_RU.md.

В репозитории уже существует независимая линия QKF-Certifier. Этот каталог ведёт линию QKF → AI из чата, с собственной нумерацией Run26. Он не меняет смысл сертификатов установленного qkf, research/CURRENT.md или результаты другой линии.

## Гипотезы и наблюдения

1. Если прямой SQL без SDK воспроизводит нарушение, SDK не необходим для данного воспроизведения.
2. Если нарушение видно только после producer exit или позднего capture, но отсутствует после commit/close, это локализует наблюдаемую границу; причина файлового поведения без трассы VFS остаётся открытой.
3. Пара minimal / minimal_pressure различается только удерживаемыми 256 MiB Python-памяти. Различие результатов станет основанием для отдельного ресурсного опыта, но не доказательством механизма.
4. Если другая среда GitHub Actions проходит тот же frozen протокол, это ограничивает воспроизводимость. Она одновременно отличается ОС, файловым слоем и сборкой SQLite; приписывать расхождение одной причине нельзя.
5. Успех всех опытов не исправляет Run25 и не снимает блок выпуска. Изменённые fixtures, процесс наблюдения и порядок запуска могут скрыть исходный механизм.

## Зарегистрированная матрица

Два размера: первоначально n=100000 и n=300000 строк; CSV имеет n строк. Доля business-invalid 10%, повторов валидного ID 10%, уникальных валидных ID 80%; половина уникальных валидных ID уже существует. Правильный POST содержит 1.4n items и одну квитанцию. Структура таблиц предсоздана; в trial нет отдельного initialize. Первоначальные SQLite-файлы генерируются один раз в каждой среде и побайтово копируются для всех её вариантов одного размера. Их хеши сохраняются до trial. Сам генератор и независимые семантические ожидания входят в freeze; физические байты базы могут различаться между сборками SQLite.

Варианты: minimal (прямые SQL без CSV-парсера), minimal_pressure (тот же код +256 MiB), frozen ordinary, frozen staged, independently authored frozen reference. Reference — наш независимый код на стандартных механизмах SQLite, не сторонний готовый продукт. Minimal пишет малую контрольную квитанцию qkf.run26.control.v1; это не полный продуктовый контракт SDK.

* Нормальное завершение: 5 вариантов ×2 размера ×2 повтора =20 trials.
* Реальный SIGKILL: 5 вариантов ×2 момента при n=100000 =10 trials. До commit ожидается полный PRE без квитанции, после возвращения commit, до close — полный POST с квитанцией.
* Итого 30 trials, 20 обычных возвратов и 10 принудительно прерванных процессов; ожидается 25 POST и 5 PRE. Фактический exit code и достигнутый hook обязательно проверяются.

Порядок задан массивом execution_order в PROTOCOL_FREEZE.json, с ротацией вариантов в обычных сериях. json sort_keys не меняет массив. Повторы — диагностические наблюдения; статистических performance-выводов нет.

## Сбор доказательств

В actor наблюдается собственная база перед commit, после успешного возврата commit, до close и после возврата close. Дополнительно записываются product hooks, PID, монотонное время, stat identity, размеры, headers, полные SHA256 main/sidecar файлов и перечисление каталога. SQLite соединение оборачивается подклассом; vendored source не изменяется. Hashing происходит при приостановленном writer в одном потоке и меняет нагрузку опыта. Наблюдение не является трассой системных write/fsync/unlink.

После завершения subprocess родитель сохраняет exit inventory и отдельную побайтовую пару. Затем, после завершения **всех** producers и минимум двух секунд, сохраняет late inventory и вторую пару. Интервал до late разный для trials и вычисляется по timestamps; одинаковая задержка не заявляется. Все producers закрыты до холодного аудита. SHA256 считается блоками; orchestrator не материализует CSV/SQL rowsets и не накладывает тяжёлый аудит на исполнение.

Отдельный процесс cold26 запускает independently authored audit26: копирует сохранённые пары ещё раз и открывает копии обычным SQLite с нормальным восстановлением. Проверяет integrity_check, **полный** набор items, отсутствие лишних/изменённых старых значений, receipt JSON/hash/payload/counts и независимые PRE/POST ожидания. Producer-оригинал аудитор никогда не открывает SQLite. Immutable-чтение не заменяет штатный результат.

Заранее предусмотрены adversarial unit tests для обнаружения PRE+POSTreceipt, неверных строк и подделанной квитанции. Их результаты — проверка checker, а не trials успешного импорта. Все ошибки, stderr, timeout, неожиданный exit code и расхождения файлов сохраняются; никакой перебор до успеха или удаления журналов.

## Критерий

Диагностический consistency gate PASS требует всех 30 зарегистрированных records, корректных exit codes и kill hooks, совпадения producer/capture хешей, стабильных post-exit → late файлов и полного ожидаемого PRE/POST обоих captures. Любое MIXED, error, незарегистрированный journal, потерянный trial или изменённый freeze — FAIL. Gate не называется release gate: продуктивный выпуск остаётся BLOCKED из-за нерешённого Run25.

Версии Python/SQLite/compile_options, platform, доступные сведения FS записываются отдельно. Отсутствующий /proc — наблюдаемое ограничение; привилегированная трассировка не предполагается. RSS и время описательные: опыт включает полные хеши и другие observer overhead, не служит сравнением эффективности.

## Воспроизведение

Из корня репозитория, Linux/POSIX, Python 3.12:

```sh
python research/qkf_ai/run26/test_audit26.py
python research/qkf_ai/run26/test_trace26.py
python research/qkf_ai/run26/run26.py --output reproduction/qkf_ai_run26_01
```

Каталог output должен быть новым. --freeze используется только при регистрации нового протокола, не для обхода mismatch. CI проверяет сохранённый freeze; исходные данные и все traces сохраняет отдельным GitHub Actions artifact даже при FAIL. Артефакты Actions имеют ограниченный срок хранения; компактные отчёты остаются в Git.

Официальная спецификация механизма: [Atomic commit](https://www.sqlite.org/atomiccommit.html), [rollback journal format](https://www.sqlite.org/fileformat.html#the_rollback_journal). Возможность штатного восстановления не отменяет предположения механизма о файловом слое; этот опыт проверяет конкретные сохранённые результаты, а не доказывает универсальное свойство SQLite.
