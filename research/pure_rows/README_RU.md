# Pure-row initial semantics: отдельное проверяемое ядро

**Этап 38: разработан отдельно от принятого PR36; подготовлен к публикации поверх PR37.**
Ядро не импортирует PR37/signed_compact; при интеграции объединены реестр тестов
и шаги текущего workflow, сохраняя обе независимые линии.
Этот модуль вычисляет вынужденный фактор носителя, точную область определённых
значений каждой неполной строки и равенства на именованном интерфейсе. Он не
выбирает достройку вместо вычисления следствий. Это исследовательский API;
устанавливаемый `qkf`, signed-маршруты и старые сертификаты не переключены.

## Математический контракт

Основание — статья I «Initial semantics of incompletely specified actions:
forced quotients, kernel saturation, and completion», v1.0, 13.09.2026:
Theorems 3.4, 4.1, 5.2, 5.3, Proposition 5.4, Theorems 6.5–6.6 и §10.
Речь идёт **только о двухсортном pure-row ground-фрагменте**.

Вход содержит непустые конечные A и B, полные таблицы их нативных операций
положительной арности и список уравнений `alpha(b,a)=c`. Имена элементов —
выделенные константы, НЕ нульместные нативные операции, сохраняемые строкой.
Список может содержать одинаковые вхождения и разные выходы при одном входе.
Семантика НЕ предполагает частичную функцию до факторизации.

Компилятор задаёт ровно `D_A ∪ D_B ∪ Comp_A ∪ Gamma`: совместимость действия
с каждой нативной операцией A только на именованных входах. Операции разных
сортов и свежий символ действия внутренне различаются, даже при совпавших
текстовых метках. Таблица операции B **не добавляет закон композиции действия**.
Никакие тождества разновидности на неназванных элементах не предполагаются.

Не поддерживаются в этом контракте дополнительные Un/Comp/Inv, односортное
связывание, смешанные нативные операции, универсальные аксиомы на произвольных
элементах и нульместные сохраняемые операции. Неизвестные поля/теории отвергаются.

## Вход и выход

```json
{
  "schema": "qkf-pure-row-input-v1",
  "theory": "typed-ground-pure-rows-v1",
  "carrier": {
    "names": ["0", "1", "2"],
    "operations": [
      {"name": "f", "arity": 2, "table": [0,0,0,0,0,0,0,1,0]}
    ]
  },
  "operators": {"names": ["b"], "operations": []},
  "cells": [[0,2,0]]
}
```

Индексы таблиц — лексикографический порядок кортежей, последний аргумент меняется
быстрее. `cells` содержит `[operator_index, input_index, output_index]`.
Результат `qkf-pure-row-result-v1`, `status: certified` означает **точное
вычисление следствий данного ground-входа**, НЕ правильность Java-программы и
НЕ отсутствие конфликта между исходными различными именами.

Отдельно возвращаются:

* `carrier_partition`, `quotient_size`, `quotient_operations`: Q = A/theta;
* для каждой строки: S, h, ker(h), kappa = Cg_Q(ker h), D = S^kappa,
  вынужденные значения и внешние kappa-классы;
* разбиения именованного интерфейса на горизонтах 1 и 2, N1/N2,
  горизонты первого контакта ячейки с носителем;
* траектория синхронной обратной связи и число строгих шагов.

В данных строки индексы относятся к **Q**, а не непосредственно к A.
`carrier_partition` задаёт соответствие. `null` в `forced_values` означает
внешнее начальное значение, не «произвольный элемент Q», не ошибку вычисления
и не операцию с частично определённой семантикой.

Именованный интерфейс упорядочен как имена A, затем все alpha(b,a) построчно.
Он не объявляется замкнутой подалгеброй. Общая начальная алгебра может быть
бесконечной даже при конечном представленном интерфейсе.

## Что находится в сертификате

`qkf-pure-row-certificate-v1` содержит пять проверяемых частей плюс сохранённый
результат. Внешний проверяющий заново получает исходный input; SHA-256 связывает
каноническую JSON-структуру, сохраняя порядок вхождений. Это не хеш авторства и
не замена проверки уравнений.

### 1. Точная синхронная обратная связь

Начиная с диагонали A, для **всех** строк на текущем Q строятся две копии Q,
связанные проекциями заданных ячеек. Локальная raw-pushout конгруэнция
проверяется по нативным таблицам двух копий, без автоматического alpha-feedback.
Её центральный kernel поднимается на A. Следующий шаг — точный join этих
поднятых kernels как нативная конгруэнция A. Все строки раунда видят один Q,
а не промежуточное обновление от предыдущей строки.

Последний раунд обязан быть общим фиксированным пунктом. Промежуточные раунды
строгие; их не более |A|-1. Нижняя сторона каждого слияния подтверждается
выводом, верхняя — полным выполнением правил замыкания. Поэтому нельзя начать
с произвольного более грубого «удобного» фактора или остановиться раньше.

### 2. Генерация S, точный kernel и насыщение

Каждый элемент S имеет шаг происхождения: заданное вхождение или нативная
операция на уже полученных элементах. Проверяется замкнутость S, все заданные
ячейки и гомоморфность h. Отдельный сертификат устанавливает **точно**
Cg_Q(ker h), снова с обоснованием слияний и замкнутостью.

Проверяется условие защиты `kappa ∩ S² = ker h`. На защищённой строке D
вычисляется как объединение kappa-классов, пересекающих S. Их значение — h(s)
для любого такого s. Внешние части разных строк не отождествляются между собой.
Пустая строка имеет S=D=empty и диагональный row-kernel на Q.

### 3. Хронологические выводы равенств интерфейса

Вторая, намеренно избыточная часть сертификата задаёт полные равенства на I
для горизонтов 1 и 2. Шаги — `seed`, `native`, `feedback`. Аргументные равенства
конгруэнтного шага должны уже следовать из предыдущего префикса журнала. DSU
лишь проверяет эту транзитивность; checker не запускает процедуру насыщения.
Продуктивные шаги не превосходят |I|-1. Подмена partition без вывода запрещена.

На горизонте 1 нативные записи есть только в центре, вместе с заданными
ячейками и alpha-конгруэнцией. На горизонте 2 добавляются нативные таблицы
строк через совместимость. В конце проверяются **все** записи и feedback,
а не только использованные в коротком положительном выводе.

### 4. Конечные разделяющие модели

Сертификат предъявляет полную интерпретацию через конечные таблицы с явным
значением по умолчанию для неуказанных кортежей. Checker вычисляет все
активные исходные уравнения — нативные диаграммы обоих сортов, вхождения
и (на горизонте 2) всю совместимость. Каждый интерфейсный терм должен
получить именно свой класс; разные заявленные классы разделяются одной моделью.

Это верхняя сторона точности, независимо от журнала положительных слияний.
На горизонте 1 разделитель **может нарушать более глубокую совместимость**.
На горизонте 2 он обязан удовлетворять всему входному E. Выбор default —
свидетельство существования модели, не утверждение о каноническом значении.
В частности, от модели не требуют законов полурешётки на смешанных/внешних
кортежах лишь потому, что именованная A является полурешёткой.

### 5. Согласование структурного и интерфейсного результата

Разбиение из Q, h, kappa и внешних классов должно совпасть с проверенным
полным интерфейсом. Проверяются формулы N1/N2, вложение отношений горизонтов
и значения carrier-contact. Сохранённый `result` сравнивается с полностью
пересчитанным результатом, а не принимается как квитанция.

Глубины 1/2 относятся только к данному фиксированному неглубокому фрагменту.
Это не общий вычислитель всех lambda/delta статьи II, не длина переписывания
и не число раундов обратной связи. В острой семье статьи I число раундов
доходит до n-1, хотя конечный горизонт равен двум.

## Выбор достройки — отдельное обязательство

`check_completion` принимает `qkf-pure-row-completion-v1` с выбранным
carrier partition и полными maps Q→Q для всех строк. Он проверяет нативную
конгруэнцию, гомоморфность каждого map и заданные ячейки. Результат
`completion_verified` доказывает существование **этой** выбранной достройки
на **этом** факторе. Он не доказывает минимальность фактора и не меняет
внешние значения в ранее установленной начальной семантике.

Production API не перечисляет все repairs и не выдаёт сертификаты отсутствия
достроек. Малые отрицательные/несравнимые repair-примеры остаются независимыми
исчерпывающими проверками прежнего прототипа, а не новым общим repair-solver.

## API и CLI

```python
from research.pure_rows.producer import prove
from research.pure_rows.checker import check, explain, check_completion

result, certificate = prove(presentation, {"max_events": 100000})
if certificate is not None:
    verified = check(presentation, certificate)
    query = explain(presentation, certificate, left=0, right=2, horizon=2)
```

```sh
python -m research.pure_rows prove input.json --proof proof.json
python -m research.pure_rows check input.json --proof proof.json
python -m research.pure_rows explain input.json --proof proof.json --left 0 --right 2 --horizon 1
python -m research.pure_rows check-completion input.json --proof chosen-map.json
```

`explain` сначала проверяет полный сертификат. Ответ `not_forced_equal`
содержит разделяющую модель; он не утверждает, что равенство невозможно во
всех моделях. Положительное объяснение сохраняет полный конечный журнал;
оптимальность размера или минимальность поддержки не заявляются.

CLI не перезаписывает существующие файлы и не выдаёт частичный proof при
исчерпании бюджета. Коды: 0 — проверенный результат/вывод/выбор достройки;
2 — бюджет; 3 — невалидный сертификат; 64 — ошибка входа/файла.

## Ресурсы и доверенная часть

Текущий явный профиль: 1–32 имени каждого сорта, до 16 операций на сорт,
арности 1–4, не более 8192 записей всех таблиц на сорт и 200000 представленных
нативных записей копий. До 4096 вхождений ячеек. Это инженерные пределы,
не математические предпосылки теоремы. Пустая нативная сигнатура разрешена.

Бюджеты production: `max_events` (по умолчанию/потолок 100000), `max_work`
(5000000, допускается до 20000000), `max_rounds` (32, включая заключительную
проверку фиксированного пункта). Нулевой бюджет разрешён и может дать
`budget_exhausted`, никогда неполный точный ответ. Счётчик work считает
сканы генератора, не CPU-инструкции checker. Проверка имеет собственные
жёсткие ограничения JSON, таблиц и длины продуктивных журналов. Если
построенное доказательство превышает пределы представления, producer возвращает
`budget_exhausted` на стадии `certificate_encoding`, без частичного proof.

Доверенная реализация: schema/compiler конечного входа, элементарные таблицы,
проверки правил, partition/model checker и Python. Структурный алгоритм и
checker разделены; оба используют элементарные функции данных. Никакие
producers, старый прототип, ground-oracle, SMT, Java или signed-модули не
импортируются из checker. Новой Lean-теоремы нет (`lean_checked: false`).

## Происхождение и проверка

Алгоритмы feedback, raw-row closure, quotient и row geometry адаптированы из
неизменного `papers/paper_I/verification/verify_article.py` (MIT). Его SHA-256:
`dd1be10b8f242740d628865087dde5025510b2d7a861c0a65ed64371c5e50a91`.
Они не выдаются за вновь изобретённые алгоритмы. Новое — самостоятельный
контракт обмена, явные нижние и верхние доказательства, строгий checker,
типизированный input, budgets, CLI и независимое воспроизведение.

`reference.py` отдельно строит RAW двухсортные ground-уравнения и их подтермы,
включая alpha(b,f(...)) до свёртки нативной таблицы. Он сравнивается с новым
результатом на обоих горизонтах. Дополнительно вызывается сохранённый
структурный прототип. Эти сравнительные алгоритмы запрещены во время replay.

```sh
python -m unittest research.pure_rows.test_pure_rows -v
python -O -m unittest research.pure_rows.test_pure_rows -v
python -m research.regression.run --group prior
python -m research.pure_rows.experiment reproduction/pure_rows
python -m research.pure_rows.replay reproduction/pure_rows
python -O -m research.pure_rows.replay reproduction/pure_rows
```

Тесты покрывают математические разграничения, испорченные выводы/модели,
неполное замыкание, лишний фактор, отсутствующие guards kernel-extension,
положительные арности, типы/лимиты, отдельные completion witnesses и строгие
импорты. Эксперимент фиксирует 16 именованных, 5120 исчерпывающих двухэлементных
и 128 seeded mixed-примеров, всего 5264. Сохраняются все input+proof, размеры,
поиск, встроенная проверка, отдельный replay, независимая reference-работа и
неудачные попытки бюджетов. Ни один из них не является Java-программой или
внешним holdout. Глобального выигрыша скорости не заявляется.
