# PR42: source-bound вынужденность локальной ascending-ячейки

Реализован зарегистрированный в PR40 пилот: из четырёх source-bound ячеек
получается значение вне порождённой области `S`, с независимым consumer proof.
Для исходного Graal-контекста `|S|=4`, `|D|=8`, `h({A,B})=∅`.
На forcing-пути нет прямого запроса этой ячейки.

Решение A1: механизм принят только в данном локальном профиле. Экономическое
преимущество I не установлено. Прямой Boolean/range-вывод на тех же seed-фактах
короче и не требует насыщения; рекомендуемый выбор для этого пилота — direct.
PR43 может продолжать query/planner/reuse независимо от результата I.

## Контракт и граница утверждения

Профиль `graal-ascending-physical-phases-v1` относится к **одной nonsign ячейке**
восходящего repair-цикла `computeLowerBound`. Фазы:

| Индекс / бит | Фаза | Смысл |
|---|---|---|
| 0 / 1 | A=(false,0) | Первый optional бит ещё не инкрементирован |
| 1 / 2 | B=(true,0) | Инкремент уже был, физического carry нет |
| 2 / 4 | C=(true,1) | Инкремент уже был, есть физический carry |

Наблюдение — битовая маска подмножества этих **различимых физических фаз**.
Запрос связывает `(m,a,g,y)`: must, may, входной бит, наблюдаемый выход.
Проверяется `m≤g≤a`; все четыре значения — биты. Цель `[P,V]` утверждает
`h(P)=V`, где `h(P)={q : out(q)=y ∧ next(q)∈P}`.
Можно запросить до 16 целей; повторные цели используют обычный кеш.

Исходник целиком проходит прежний `lower_source.compile_source`: проверяется
полная поддержанная форма выбранного helper и связанные native helper bodies.
`carry_kernel.source_cell` исполняет только три фазы **выбранного** label.
Это не frontend для произвольной Java и не проверка всех методов файла.
Предусловие нахождения в данном локальном source-контексте принимается явно.
Новое доказательство не устанавливает достижимость фазы из начала программы,
simulation/gluing целого слова, всего helper или signed-профиля PR41.

## Source-факты и доказательство моста

Каждая из трёх ветвей содержит incoming addition, фактически выполненные repair
инструкции с промежуточными состояниями, выход и следующую физическую фазу.
Producer сверяет окончание с сохранённым `source_cell`. Независимый checker
повторяет арифметические шаги и проверки branch guards, не вызывая `source_cell`
и не импортируя producer. Пропущенная, лишняя или подменённая инструкция отвергается.

Каждый seed имеет явные зависимости от всех трёх branch proofs. Checker заново
проверяет каждое membership-обязательство. Receipt, хеш или проектная таблица
из PR40 не заменяют это доказательство. Хеши source, полного compiled IR,
запроса, profile и ruleset привязывают переносимый proof к точному контексту.

`Q=P({A,B,C})` имеет восемь элементов и две бинарные операции. В proof переданы
все 128 записей union/intersection, и checker проверяет значение каждой записи
на конкретных подмножествах. Дополнительные операции, в том числе абсолютное
дополнение, не допускаются.

После проверки ветвей известно, что реальное локальное действие задаётся
детерминированным переходом в тот же набор физических фаз. Для каждого `q`
положим `k=[out(q)=y]`, `u=[next(q)∈P]`, `v=[next(q)∈R]`. Проверка восьми
Boolean случаев доказывает
`k∧(u∨v)=(k∧u)∨(k∧v)` и `k∧(u∧v)=(k∧u)∧(k∧v)`.
Это гомоморфность **фактического** guarded inverse image для любых `P,R`.
Таблица восьми значений `h` для этого не вычисляется.

Далее сохранённый `research.pure_rows` проверяет свою точную конечную теорию:
нативную диаграмму, ground compatibility, seed cells, kernel saturation,
хронологические derivations и разделяющие модели. Новый мост допускает только
защищённый носитель и тождественный descent. Склейка двух различимых source
наблюдений отвергается, даже если абстрактная pure-row теория допускает quotient.
Поэтому вынужденное равенство в этой теории действительно для проверенного
source-действия. Утверждения старого checker за пределами его scope не расширены.

Trusted boundary: сохранённый restricted compiler и его native contracts,
интерпретация физической ячейки, Python-проверка арифметических/Boolean правил,
нативной диаграммы и pure-row evidence. Это не новый Lean theorem и не Java
runtime validation. Тесты отдельно сопоставляют обе cell-реализации с целочисленным
исполнением repair-инструкций на всех 48 комбинациях поддержанных действий,
mask/input cells и физических фаз.

## Почему требуется насыщение

В пилоте `(m,a,g,y)=(0,1,1,0)` получены `A→(0,C), B→(1,B), C→(0,C)`.
Source-bound seed cells:

| P | h(P) |
|---|---|
| ∅ | ∅ |
| {B} | ∅ |
| {B,C} | {A,C} |
| {A,B,C} | {A,C} |

Эти четыре входа уже образуют подалгебру `S`. Их ядро содержит
`∅~{B}` и `{B,C}~{A,B,C}`. Пересечение второй пары с `{A,B}` даёт
`{B}~{A,B}`, а значит `{A,B}~∅`. Это обеспечивает требуемый ответ
`h({A,B})=∅` вне `S`. В ambient kernel два класса:
`{∅,{A},{B},{A,B}}` и `{{C},{A,C},{B,C},{A,B,C}}`.
Оба имеют контакт с `S`, поэтому `D=Q`.

Consumer conclusion: при указанном локальном guard невозможно одновременно
выдать 0 и завершить ячейку без физического carry. `no_saturation` проверяет
только порождённую область и оставляет эту цель `unresolved`.

## Прямые контроли и стоимость

`direct_seeds` получает **те же четыре source-факта и branch proofs**.
Пусть `K=h(ABC)`, `b=h(B)`, `bc=h(BC)`. Из проверенного concrete inverse image
следуют образы отдельных фаз `K\bc`, `b`, `bc\b`. Объединение нужных атомов
даёт любой запрошенный образ. Здесь используется относительная разность внутри
output guard; гомоморфность абсолютного дополнения не предполагается.

`direct_cell` — более дешёвый холодный контроль: те же три физических branch
proofs, membership только запрошенных целей, без покупки четырёх seed и native
tables. Обе direct-стратегии имеют кеш; их не заставляют платить за чужое
насыщение или ненужную нативную диаграмму.

В этой серии seed не нужны независимым целям и полностью оплачены. Все пути
вычисляют три физических source-cell перехода; forcing не экономит эту работу.
Он экономит только явный запрос производной action-ячейки, ценой seed, таблиц
и насыщения. Полная локальная transition map из трёх фаз **уже известна** при
построении seed. Это раскрыто в ledger и не выдаётся за отсутствие source work.
Глобальные `source_quotient`, `replay_rows`, legacy builders не вызываются.

Сценарии 1/4/16 относятся к одной подготовке и четырём различным целям максимум.
При 16 целях есть 12 повторов, доступных обычному кешу любого маршрута.
Proof содержит всю подготовку и переносим без тёплого кеша процесса. Cold proof
и shared batch proof имеют одну полную подготовку; межпроцессного кеша нет.

Ledger считает реальные вызовы, source admission, branch replay, все seed,
таблицы, compatibility/descent, pure-row work, цели и размер proof. Время
подготовки/маршрута/проверки вынесено отдельно. Оно инструментировано, порядок
последовательный, module caches между случаями сохраняются; это не benchmark
ускорения. Runtime trace и его хеш — диагностика, а не криптографическое
доказательство того, какой код исполнялся.

## Воспроизведение

Из корня репозитория, Python 3.10 или 3.12, без новых зависимостей:

```bash
python -m research.regression.run --group new
python -O -m research.regression.run --group new
python -m research.source_forcing.preserve
python -m research.source_forcing.experiment reproduction/source_forcing/fresh
python -m research.source_forcing.replay reproduction/source_forcing/fresh
python -O -m research.source_forcing.replay reproduction/source_forcing/fresh
```

`fresh` должен отсутствовать: результат предыдущего запуска не перезаписывается.
Fresh replay ставит запрет импорта producers, native discovery, прямых
генераторов и SMT **до** загрузки checker. Отдельный call guard действует и
для уже импортированных global builders. Поиск при budget exhaustion повторно
не запускается; такая диагностика не является семантическим сертификатом.

Пример запроса:

```json
{"schema":"qkf-local-forcing-request-v1","profile":"graal-ascending-physical-phases-v1","label":[0,1,1,0],"goals":[[3,0]]}
```

```bash
python -m research.source_forcing prove research/graal/previous/baseline/source/IntegerStamp.java --request request.json --proof proof.json
python -m research.source_forcing check research/graal/previous/baseline/source/IntegerStamp.java --request request.json --proof proof.json
```

`--route direct_seeds`, `direct_cell`, `no_saturation` выбирают контроли.
Коды: 0 — certified; 1 — refuted/unresolved/unsupported/budget; 2 — неверный
вход/proof или попытка перезаписи. Refuted означает ложное равенство локальных
множеств с разделяющей физической фазой, а не контрпример целой Java-программы.
Подробные результаты и решение A1 — в `VALIDATION_RU.md`.
