## Ориентир

QKF должен стать системой, которая по исходной семантике, условиям применимости и независимо заданному обязательству строит достаточный наблюдательный интерфейс действия, обосновывает его и компонует с другими такими интерфейсами.

Главный показатель продвижения — какая часть доказательной конструкции больше не требует ручного задания. Покрытие, стоимость обнаружения, размер сертификата, стоимость replay и формальная проверенность измеряются отдельно.

Математическая основа: Paper I, теоремы 3.4, 4.1, 5.2, 7.1; Paper II, разделы 4 и 7; Paper III v2.0, разделы 7, 9 и 12. Дальнейшие пункты — предлагаемая инженерная и исследовательская программа, а не новые результаты этих статей.

## Что уже существует и не должно быть изобретено повторно

В research/inference/v3_adapters.py есть source-derived residual questions и terminal continuations с MAX_TERMINAL_LOOKAHEAD = 2. Это не единственные вопросы v3: сохраняются Boolean projections, integer cuts/equalities и pairwise relations.

В research/observations уже описаны: замыкание вопросов обратным переносом через переходы, стабильный конечный фактор, разделяющие контексты, плотное и компактное атомное представления вынужденных строк, восстановление переходов из строк. Общий JSON finite model сам по себе является доверенной спецификацией, а не доказательством связи с внешним Java-исходником. Source-bound мосты уже есть в отдельных старых профилях.

Поэтому ближайшая работа — соединить существующие механизмы с signed-путём, а не объявлять само finite-state refinement или atomic encoding новой разработкой.

## Блок A: семь ближайших PR

### PR #26 — Зафиксировать исходную точку, карту механизмов и протокол оценки

**Цель.** Сделать v3 неизменным baseline до дальнейшей разработки.

**Работа.** Добавить roadmap и обновляемую карту «утверждение → модуль → сертификат → проверка → ограничение». Зафиксировать transitive engine dependencies, версии, семантические контракты и бюджеты. Подготовить research/external/frozen_v3/ENGINE.json и PROTOCOL.md. Сначала опубликовать правила отбора и фиксацию движка, затем CORPUS.json с точными source blobs и независимыми спецификациями; оба шага — до вычисления результатов. На этом PR CI проверяет протокол, хеши и тестовые примеры, но не преждевременно исполняет оценку.

**Отбор.** Новые источники выбираются по объявленному правилу, не по успеху инструмента. Ранее использованные методы и близкие копии отмечаются явно. Спецификации выводятся из документированного назначения, не из удобной версии цели. Все подходящие по правилу методы остаются в знаменателе.

**Готово, когда.** Зафиксирован воспроизводимый baseline и можно проверить, что первый измеряемый запуск ещё не менял движок. Исторический frozen_v2 и его 1/15 не затронуты.

**Не входит.** Расширение Java, новые наблюдения, новый proof engine или обещание процента успеха.

### PR #27 — Провести внешний baseline v3 без настройки по результатам

**Цель.** Измерить переносимость текущего решения и место остановки каждой задачи.

**Работа.** Запустить зафиксированный корпус, сохранить все результаты и причины остановки: исходный профиль, язык цели, модель, inference, бюджет или target obligation. Измерить discovery, replay, память, размеры модели/фактора/сертификата. Выполнить независимый replay и объявленную конечную native-валидацию там, где она применима.

Парное сравнение с frozen v2 допустимо для одинаковых семантических обязательств; отсутствие у v2 нужного языка цели сохраняется как capability gap. Не заменять положительную степень двойки на popcount=1 ради сравнения.

**Готово, когда.** Все зарегистрированные методы получили результат, ошибка инфраструктуры не названа опровержением, сертификаты и реальные контрпримеры проверены. Движок не менялся между фиксацией и оценкой.

**Правило дальнейшего использования.** После просмотра и использования результатов при разработке этот корпус становится reference/development для последующих версий. Его нельзя повторно объявить независимым holdout нового движка. Неудача реализации оформляется как нарушение/новый запуск протокола, а не исправляется незаметно.

### PR #28 — Source-bound мост от signed-исходника к observation-ядру

**Цель.** Дать существующему общему ядру конечную signed-модель, не доверяя таблице, присланной генератором.

**Работа.** Добавить адаптер разрешённого Java-профиля: исходник → IR → достижимая модель → вход существующего observation-checker. Зафиксировать source/entry/type/semantics bindings, исходное состояние, алфавит, выходы, terminal-consumer и допустимые завершения. Checker восстанавливает модель из исходника и проверяет её полное покрытие, а не принимает хеш произвольной JSON-таблицы как доказательство.

Явно согласовать границу пустой трассы и положительной ширины. Не молча наследовать разные ограничения: общий finite Model сейчас имеет предел 64 состояния, тогда как residual-путь v3 допускает 512. Первый мост либо объявляет пересечение бюджетов с отдельным budget_exhausted, либо получает отдельно проверяемое расширение — не ослабление полноты.

**Готово, когда.** Изменения исходника, terminal-метки, начального состояния и пропуск достижимого перехода обнаруживаются. Старые сертификаты и схемы продолжают проверяться своими checkers.

**Граница.** Доказана связь в принятой остаточной семантике; полная корректность Java frontend не объявляется формализованной.

### PR #29 — Подключить существующее замыкание наблюдений к signed-модели

**Цель.** Убрать зависимость нового signed-маршрута от заранее перечисленных продолжений длиной до двух.

**Работа.** Переиспользовать вывод вопросов из consumer-меток и их обратный перенос через переходы. Добавлять вопрос, когда он действительно уточняет наблюдательную алгебру, и останавливаться только при проверенной устойчивости либо явном исчерпании бюджета. Сохранять происхождение вопросов и существующие разделяющие контексты; расширять общий код только там, где мост выявит реальную несовместимость.

**Проверки.** Development-модели с различением лишь после продолжения длиннее двух; допустимые переименования и эквивалентные варианты source-профиля; отдельная проверка выведенного фактора и контекстов старым независимым finite-model oracle.

**Готово, когда.** Новый signed-путь строит интерфейс без переданного partition, набора вопросов и фиксированного двухбитного cutoff. При заявлении coarsest factor это подтверждается относительно точно объявленной конечной модели и consumer. Поисковый предел не выдается за доказательство неразличимости.

**Что не заявляется.** Старый v3 не обязан проиграть delayed-пример: его residual-вопросы могли уже быть достаточны. Новый результат — интеграция более общего способа получения интерфейса, не автоматическое расширение Java и не новый алгоритм минимизации автоматов. Длина separating word не является λ_E из Paper II.

### PR #30 — Подключить вынужденные строки к реальному исполнению фактора

**Цель.** Сохранить содержательный алгебраический путь QKF, а не приложить к минимизированной таблице декоративное доказательство.

**Работа.** Использовать существующее atomic row encoding для выведенного signed-фактора. Проверить нативные атомы строк h(P) = G ∩ φ⁻¹(P), их метки и guards; восстановить требуемое действие через уже проверяемое completion-правило. Новый factor runner должен получать выходы/переходы из проверенного row-пакета. Прямая таблица остаётся контрольным маршрутом для differential tests, а не скрытым источником успешного verdict.

**Проверки.** Перестановка меток при неизменном ядре, повреждение атома или guard, одноэлементный фактор и пустой guard. Сравнение atomic и полного представления на небольших моделях без обязательного раскрытия powerset на больших.

**Готово, когда.** Повреждённый row-пакет отвергается до успешной проверки цели; row-based действие совпадает с исходным для каждого разрешённого перехода; стоимость слоя измеряется отдельно.

**Граница.** Атомы здесь порождают весь нужный carrier. Это не выдаётся за реализацию общего нетривиального расширения S до S^κ из Paper I — оно относится к блоку B.

### PR #31 — Сквозной unified-маршрут с раздельной проверкой интерфейса и цели

**Цель.** Сделать новый механизм вызываемым по исходнику и цели без ручной сборки цепочки.

**Работа.** Подключить source-bound model, выведенный observation certificate и row-based runner к независимому target checker. Рабочее имя нового engine — inference-v4; новую схему вводить только для действительно нового пакета, старые не переинтерпретировать. Начальная область нового engine — signed-профиль; остальные маршруты остаются явно прежними до собственных проверенных мостов.

Разделить подтверждение source-interface, подтверждение target и реальный target counterexample. Диагностика недостаточности интерфейса — отдельный объект, не upstream bug. Сохранить явные unsupported, budget_exhausted, invalid_certificate, input_error и internal_error. Зафиксировать source, consumer, domain и внешнюю цель раздельно.

**Готово, когда.** Одна команда prove и отдельная check воспроизводят всю цепочку. В свежем процессе до загрузки checker заблокированы producer, SMT и native execution. Проверки проходят нормально и под -O. Корректный source-interface для неправильной программы не превращается в certified target.

Каждый пункт — самостоятельная проверяемая единица. Исследовательское осложнение может потребовать разделения PR; факт завершения определяется его критерием, а не количеством прогонов.

## Неизменяемые правила

1. Вынужденное равенство, допустимое наблюдательное отождествление и выбор достройки — разные утверждения. Нельзя переносить гарантии одного на другое без моста.
2. Нативная семантика, labels, domain и joint input identity — часть обязательств. Хеш даёт привязку байтов, а не доказательство семантического соответствия.
3. Цель независима от producer и не ослабляется для успешной проверки. Допустимо вывести интерфейс для этой цели, но достаточность доказывается по исходной семантике.
4. Конечная native-валидация, all-width proof и Lean theorem учитываются отдельно. Малая ширина контрпримера не автоматически переносится на Java int/long.
5. Успешный replay не импортирует поиск. Генератор недоверенный; проверяющий код и модель остаются явно заявленной доверенной частью до их формализации.
6. Успех corpus не обязателен. Обязательны сохранённый знаменатель, явные пределы, точные source/engine identities и отсутствие скрытой настройки holdout.
7. Минимальность фактора для конечной модели, неизбыточность вопросов, длина separating context, глубина доказательства и время исполнения не отождествляются.

## Точка пересмотра

После #27 можно уточнить engineering приоритеты, не меняя исходный эксперимент. После #32 выбрать следующий основной акцент: B — где общей вынужденности не хватает; C — где остановка на языке/семантике; D — где нужны совместные контексты; E — где раскрытие носителя съедает выигрыш. F и H сопровождают стабильные результаты.

Ориентир сохраняется: уменьшать объём математического интерфейса, который человек должен заранее изобретать и кодировать, сохраняя проверяемость каждого шага.
